# Gate 9 Platform Backup and Restore Runbook

> **DISPOSABLE POSTGRESQL 15 VALIDATION ONLY**
>
> These Gate 9 procedures are not production restore authorization, are not VPS deployment authorization, and do not authorize staging, Supabase, client, remote, or persistent database access. Gate 10 discussion does not authorize production use. This document intentionally contains no production restore command. Any future production procedure requires separate approval and environment-specific safeguards.

## Boundary

- Platform PostgreSQL only; Transcription and Writer/client databases are excluded.
- Loopback PostgreSQL 15 only.
- Backup source name must match `^gate9_platform_[a-f0-9]{12,32}$` and its expected-name/confirmation/current-database identities must agree.
- Restore target is generated by the script as `gate9_restore_<32 lowercase hex>` and is always a new invocation-owned database.
- The restore script physically validates and then removes only its exact target after full ownership revalidation.
- No `.env`, generic `DATABASE_URL`, application configuration, implicit connection value, or command-line credential is accepted.

## Required disposable configuration

Backup uses only:

- `G9_BACKUP_SOURCE_DATABASE_URL`
- `G9_BACKUP_EXPECTED_DATABASE_NAME`
- `G9_BACKUP_DISPOSABLE_CONFIRMATION` — exact database-name match
- `G9_BACKUP_OUTPUT_ROOT`
- `G9_BACKUP_OUTPUT_DIRECTORY` — exact direct child of the root
- optional `G9_BACKUP_RETENTION_COUNT` — default 5, accepted range 1–5

Restore uses only:

- `G9_RESTORE_ADMIN_DATABASE_URL`
- `G9_RESTORE_ADMIN_DATABASE_NAME`
- `G9_RESTORE_TARGET_OWNER`
- `G9_RESTORE_DISPOSABLE_CONFIRMATION=GATE9_DISPOSABLE_RESTORE`
- `G9_RESTORE_OWNERSHIP_ROOT`
- `G9_RESTORE_OWNERSHIP_DIRECTORY` — exact direct child of the root

Supply these values through the process environment without printing them. Do not put credentials or complete DSNs in arguments, logs, evidence, or tickets.

## Backup validation procedure

1. Independently identify a disposable loopback PostgreSQL 15 source created for the current test invocation.
2. Set the dedicated backup environment variables. Ensure expected name and confirmation exactly equal the disposable database name.
3. Ensure the configured output root exists, is explicitly owned for this validation, and contains no links, junctions, mount substitutions, or reparse points.
4. Run `python scripts/operations/platform_backup.py`.
5. Retain its sanitized JSON stdout as evidence. Never retain or reproduce the environment.
6. Confirm one complete direct-child group exists: custom-format dump, SHA-256 sidecar, and sanitized manifest.
7. Confirm the manifest contains the tool-directory/group identities, PostgreSQL 15 versions, artifact size/hash, Platform counts, and Alembic revision but no host, user, DSN, password, or credential.
8. Confirm `pg_restore --list` evidence includes Platform tables and `alembic_version`.

The script performs all client/server, loopback, source-name, authorization, and current-database checks before creating its directory marker or artifact group. It invokes `pg_dump` with custom format, no owner, and no privileges. Credentials reach the child only through a private environment.

## Retention behavior

- The output directory is usable only with its valid atomic `.gate9-platform-backup-owner.json` marker.
- Only complete regular direct-child groups whose manifest matches that directory marker are eligible.
- Cleanup is nonrecursive, never follows manifest-provided paths, and never deletes directories, unknown files, partial groups, links/reparse points, or unowned files.
- Validated groups older than seven days or beyond the configured 1–5 group limit are removed file-by-file.
- Any ownership or containment ambiguity refuses cleanup.

## Restore validation procedure

1. Use only a complete artifact group produced by the backup procedure above.
2. Independently identify a loopback PostgreSQL 15 server and explicit administrative database/role dedicated to the disposable test environment.
3. Set the dedicated restore environment variables. Never supply a target database name; the script generates it.
4. Ensure the ownership root exists and is explicitly owned for this validation.
5. Run `python scripts/operations/platform_restore.py --artifact <absolute-path-to-disposable-dump>`.
6. Confirm sanitized output reports PostgreSQL 15, restored counts/revision/constraints/indexes, and `cleanup_completed=true`.
7. Independently confirm the generated target no longer exists and that the invocation sidecar was removed after successful cleanup.

Before target creation, the script validates the artifact group, exact `pg_restore --version` output, connected loopback identity, and six-digit PostgreSQL 15 `server_version_num`. It creates an invocation sidecar, generates a cryptographically random target, records ownership as a database comment, and verifies name/owner/marker in system catalogs before `pg_restore --exit-on-error --no-owner --no-privileges`.

Immediately before DROP, it revalidates the connected loopback server, exact target, owner, database marker, and local sidecar. Any mismatch causes cleanup refusal and sanitized manual-cleanup evidence. Never respond to that warning with a pattern-based or guessed DROP.

## Exit-code evidence

- 0: success.
- 2: configuration, authorization, bounds, identity, or safety/precondition rejection.
- 3: missing, malformed, or non-15 PostgreSQL client/server version.
- 4: validated operational/database/subprocess failure.
- 5: artifact, checksum, manifest, ownership, containment, post-operation validation, or unexpected internal failure.

All stderr is sanitized. Raw subprocess stderr, exception representations, tracebacks, complete DSNs, environment contents, and connection command lines are not valid evidence and must not be emitted or copied.
